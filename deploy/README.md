# SourceLoom 生产部署

这是当前处理器的唯一有效部署入口。正常流程为原件导入 → 单包交接 → 返回稿导回 → 资源恢复 → 阅读、保存与交付；手动交接和自动交接共用该工作台。仓库提交、CI、回环健康检查与正式站验收是不同结果，分别记录。

## 1 实际运行边界

默认只需要 [网页服务](sourceloom.service) 和现有 HTTPS／登录代理。`python -m sourceloom.cli serve` 绑定 `127.0.0.1`，不信任外部代理头。当前处理器上传在网页服务的请求线程中解析；已明确请求的自动交接由网页服务内部执行器处理，不依赖历史生成 Worker。历史接入路由使用的独立解析子进程不是处理器上传的运行方式。

正常安装不启用旧生成 Worker，也不要求额外复制外部写作 Skill。处理器任务包使用产品中已冻结的写作要求；历史生成入口仍有自己的 Skill 配置需求。历史任务读取不需要后台继续生成，确需恢复历史任务时单独使用 [历史服务说明](historical/README.md)。

本部署仅覆盖经过认证的单用户 SourceLoom，不改变 Router、ReadWeave 或其他服务。官网域名、运行用户、真实目录、账号和凭据从现有代理与服务器配置确认；本文路径是通用示例。

新材料自动生成仅允许 `execution_channel=chatgpt_web`、普通 `chat` 模式，使用用户指定的 Web-only 业务凭据。前端选项与服务端接单均拒绝 Codex、CLI、Runner 和其他供应商。历史读取不赋予继续派发权限；旧 Codex 原请求及回执保留审计，但不计入 Web Chat 验收。

## 2 安装与私有配置

需要 Python 3.11 或以上版本。每个候选使用固定提交的程序目录；不要在正在验收的目录热改代码。

```bash
# 在已核对的候选目录安装，使用独立运行环境
python3 -m venv /opt/sourceloom/venv
/opt/sourceloom/venv/bin/python -m pip install .
```

配置示例见 [认证代理配置](config.proxy.example.json)。替换授权用户与正式 HTTPS 来源；未填写 `allowed_subject` 时代理模式拒绝用户访问。默认 `provider=manual`，没有模型密钥也能手动交接；自动模式必须另行确认实际附件、结果取回能力与调用授权。

配置保存到 Git 之外的 `/etc/sourceloom/config.json`，由 [服务模板](sourceloom.service) 的 `LoadCredential` 提供。`SOURCELOOM_DATA=/var/lib/sourceloom` 是持久数据目录，运行用户必须有读写权限；私有配置与 `provider-settings.json` 不公开，数据目录只允许对应运行身份访问。已有 `provider-settings.json` 会在启动时覆盖通道配置，更新前检查其当前激活状态，不删除它来强制改变用户设置。

`processor_router` 必须独立配置获准的业务凭据与显式 Web 通道；不得继承顶层 legacy provider 密钥，不得读取 Router 的 `admin_api_key`，也不得挂载管理秘密给运行或压测进程。部署维护身份不作为生成身份使用；不因 SSH 可以读文件就认为获准消费模型。旧 Codex output-file/full 权限配置不能转成新 Web 请求，新任务遇到此配置应在派发前拒绝。

Web 目录检查是能力取证，不代表附件、档位或长文已经通过真实验收。不把 Codex effort 参数搬到 Web 请求；依据目录和页面确认当前档位。能力或登录不足时保留明确阻断，可继续手动导回及非生成工作，不换 Key、账号或通道。权限审计及 Web-only 边界验证完成后才恢复真实 Web 压测；负向通道测试必须隔离并阻止上游执行，不在生产用 Codex 试探鉴权。

```bash
# 按真实目录和服务名核对后安装模板，不复制 historical 下的服务
sudo install -m 0644 deploy/sourceloom.service /etc/systemd/system/sourceloom.service
sudo systemctl daemon-reload
sudo systemctl enable --now sourceloom.service
sudo systemctl status sourceloom.service
curl --fail http://127.0.0.1:14420/health
```

模板默认工作目录 `/opt/sourceloom/app`、运行用户 `sourceloom`。发行目录可以由该路径指向当前固定提交；虚拟环境也须安装对应代码。确认进程实际的 `SOURCELOOM_CONFIG` 已展开为对应服务的 `/run/credentials/.../config.json`，不能是字面的 `%d/config.json`；服务改名时同时核对凭据目录。不得打印配置秘密来验证路径。

确认 SourceLoom 自己的旧 Worker 没有继续写入待迁移库；停止或禁用仅属于本次授权的历史 SourceLoom 服务，不触碰其他项目。不要给共享数据目录再启动一个写入同一材料的临时实例。

## 3 HTTPS、身份与资源保护

私有配置使用 `auth_mode=proxy`、唯一 `allowed_subject` 和真实 `public_origin`。应用检查以下条件：

- 后端连接来自回环地址。
- 代理传入 `X-AIALRA-Authenticated: 1`，并且 `X-AIALRA-Sub` 精确等于配置的用户身份。
- 修改请求使用正式来源及 `X-SourceLoom: 1`；正常工作台会发送操作标记。

登录代理必须先验证真实会话并覆盖外部传来的身份头，拒绝未授权用户；不能把用户自己填写的头当成登录证据。身份标记只在受保护的代理到后端链路中设置，不把后端端口暴露到公网。

保护必须覆盖 `/`、`/api/`、PDF、图片、原件、任务包、导出和预览，不能仅保护首页。应用自身只将 `/health` 排除在身份校验之外，代理可将它限于内部探测；健康成功不证明私人资源保护成功。反向代理若有上传大小或超时限制，应与下节的产品边界协调，不因只配置首页而遗漏资源路由。

外部地址必须是官网 HTTPS 地址。内部回环请求可继续使用回环地址，但浏览器下载、任务包、来源回查和 ReadWeave 笔记链接不得依赖开发机磁盘或用户自己的 `127.0.0.1`。`readweave_url` 是服务端调用地址；若它是内部地址，另设 `readweave_public_url` 为用户能访问的正式地址，浏览器笔记链接使用后者。不设置此可选字段时沿用 `readweave_url`，仅当该地址本身对用户可用时适合这样配置。是否导入成功以原操作回执与独立读回为准，不顺带修改 ReadWeave 服务。

匿名验收至少分别请求材料列表、正文、已知原件 URL、图片、任务包和导出，确认不能读到私有字节；再用真实登录会话核对相同路径。不要把一个 200 的登录 HTML 当作原件接口的授权通过。

## 4 增量迁移与切换写入端

迁移代码和迁移材料分别执行。先清点两端材料 ID、原件摘要、正文版本、目录、资源引用、历史操作、未决请求与 ReadWeave 关系；同名不等于同一材料，相同原件也可能有独立改稿。

1. 在暂停对应写入的窗口创建一致的数据库备份，保留其引用的原件、资源、私有配置和必要恢复记录；演练恢复并核对文件摘要及关系。
2. 在隔离数据副本中演练增量迁移，输出映射与冲突清单。不用本地整库替换线上库，不依据标题覆盖，也不丢弃线上独立修改。
3. 没有冲突的稳定 ID 保持；发生身份冲突时保留两份材料和原身份映射，显式记录处理结果。目录整理只改管理元数据，不修改正文、原始返回或版本。
4. 切换前停止两端相关写入，确认没有未确定的模型／导入操作会被重发，再应用已演练的迁移。未知请求保留原身份、费用和历史，不推定它未执行。
5. 正式站成为目标写入端后，以官网正常 UI 核对迁入材料、版本、目录、图片、回查与导入关系；本地副本仍是恢复依据，避免两端各自修改后静默覆盖。

此流程不授权重新生成或替样本修文章。派生索引、缓存和包可以根据保存字节重建；原件、已接受正文、原始返回、写作 Prompt 和 Skill 继续冻结。

## 5 固定构建验收与回滚

上线前保留上一程序、对应环境与经过验证的恢复点。线上运行提交必须与最终普通推送的提交一致，记录构建与配置口径；在官网登录后实际操作上传、手动包下载、原始返回导回、资源恢复、阅读、保存、下载与 ReadWeave 交付。

用户路径验收只通过产品正常动作完成；后台日志用于取证，不能改库、热修同次运行或替换返回字节来帮测试过关。真实新模型任务、历史回执回放与隔离故障测试分别计数。普通故障保存结果后修共享机制，冻结新构建，再完整重测受影响路径。

服务重启后核对材料、版本、目录和原请求回执仍在，UNKNOWN 不自动重发。关闭浮层、切材料与后台返回不得重置当前阅读。通过首页或健康接口不能代替这些用户路径。

回滚先暂停当前写入并保存上线后新增数据。若上一程序能够读取当前数据库，切回上一程序和匹配配置，保留当前数据继续使用；先在隔离副本验证兼容性。若数据库不兼容，保持维护状态，保留完整当前库及新增材料，再用已验证的备份恢复到隔离目录，明确处理新增写入后切换。不能把旧数据库直接盖回当前库，导致上线后材料、编辑或远端导入回执无声丢失。

验证回滚后的登录、材料、资源、保存与恢复，再开放写入；不靠删除失败记录掩盖本次结果。

## 6 实际容量与等待边界

- 单文件最多 `25 × 1024 × 1024` 字节，单次上传总量最多 `100 × 1024 × 1024` 字节，1–100 个文件；多部分请求本身还受 100 MiB 请求体检查，需为其编码开销留余量。
- 单份 PDF 最多 50 页，结构最多 5,000 个对象；不能把输出文件名写“完整”当作范围核对。
- 当前处理器上传受文件、页数、对象数量和网页服务的 systemd 资源限制约束，没有独立解析子进程的 75 秒等待上限。历史接入路由的隔离解析才使用 75 秒等待、Linux CPU 60 秒及地址空间 768 MiB 限制；不能把它们算作处理器上传的保证。
- 登录代理的等待期限须与完整上传实际耗时核对。网关超时不证明原上传未保存：先从材料列表打开原记录，核对原件与进度，不盲目再次上传。PDF 几何解析复用文档和页级信息，避免逐图重新解码同一页。
- 这些是上传与解析限制，不是内容生成时限，也不保证某个模型能读任意 ZIP。单包包含资源不证明模型已经打开图像。
- 自动交接只在通道与费用已授权时执行；UNKNOWN 保留原操作，不自动重投。旧角色顺序、逐批补丁与旧整篇重试策略不是本处理器的默认部署要求。

历史与工程回报见 [历史服务说明](historical/README.md) 和 [执行 Agent 规范](../docs/EXECUTOR_REPORTING_RULES.md)。工程回报规则不得注入模型文章要求。
