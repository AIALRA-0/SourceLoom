# APCF 工程回报适配

## 作用与来源

本文件只记录 SourceLoom 用户在 2026-10-09 明确更正的工程回报要求，以及本项目实际规则入口的适配，不安装第二套 Core，不维护另一份 Canonical Rules，不改变文章内容与写作流程

APCF 的正式名称为 APCF 智能体项目控制框架（Agent Project Control Framework），来源是已验证 v0.3.0 Closeout v2 的 framework.yaml 与 README；既有 Pilot 只在 VPS 发布副本安装，当前工作目录必须单独核对是否存在真正生效的 .agent-project-control

已安装时先读当前 AGENTS、framework.yaml、规则路由、R01/R02/R03/R20，以及 Writing/Style 接口实际指向的规范；未安装时只使用可读取、经验证的发行来源作为规则参考，并明确原生生命周期未运行，不把 reports 中的提取副本称为当前工作树安装

## 每轮先立目标，再开始执行

执行前保存实际请求与范围，建立本轮独立 CHECKLIST.md，使用未开始或进行中状态；每个目标写明在什么条件下，什么问题会导致什么后果，需要达成什么单一结果，以及如何客观判定

推荐句式为：

> 【进行中】【CL-01】【具体对象】：当……时，因……会导致……，必须……，并以……确认通过

这是目标合同，不是强迫复制模板空槽；句中的因果必须真实，独立成败的结果分别成项，不用“整体优化”“基本正常”等词代替对象和判据

执行中只根据用户变更或真实必要条件更新目标，保留身份与原因；验收之后更新状态和必要说明，不改写目标使其迎合实际输出，也不在工作结束后倒推一张全为已完成的清单

最终报告完整展示当前清单，不仅展示数量或做过哪些事；若遗漏了事前清单，必须承认这次未满足执行顺序，不能事后补文件并声称已预先建立

## 机器账本与自然语言验收分别承担职责

TEST.md 保持 Core 的 APCF-TEST-FORMAT v2，一行一个稳定 TEST-ID，五个字段和状态仍按真实 schema 保存；使用实际 test_ledger.py 校验身份、字段、状态及 CL 覆盖，不减少证据要求

用户报告的第 4 区块按本次用户明确要求，逐条改为完整自然语句，保留相同顺序、TEST-ID、CL-ID、当前状态、候选环境、实际操作、事前预期、真实结果和证据；不得合并掉某个 TEST、隐藏失败、降低判据或添加未观测结论

例如，机器账本仍可以使用五个字段，用户看到的则应为：

> 【PASS】【TEST-01】【对应 CL-01】【原件读取】：在已冻结候选的登录态浏览器中，执行者打开 S5 第 14 页原表，要求正确原件实际显示后才允许确认；实际观测到原件解码完成且确认按钮随后可用，关闭重开后位置与材料身份仍一致，因此本项通过，证据见该轮原件读取记录

这只是句法样例，不是任何一次真实验收结果，不能直接当成当前 PASS 使用

Core v0.3.0 R03/R20 和 report_contract.py 当前要求报告原样嵌入机器 TEST，用户最新要求对此构成显式覆盖；因此自然句呈现不能宣称未修改的原生 report_contract 也已通过。执行者必须区分“TEST v2 解析通过”“本项目用户回报适配完成”和“原生 Gate/Finalize 通过”，后者未运行或因该冲突无法成立时据实记录

本项目不为此新建模型阶段、Reviewer 或业务状态机；逐条对照源账本完成报告核对，框架层若需兼容自然句视图，作为上游可迁移修复建议，不在这里偷偷放宽 Core

## 术语须有真实名称与足够解释

有正式缩写时使用 `ABBR 中文名称（English Full Name）`，没有正式缩写时使用 `中文名称（English Name）`；全角括号只放对应英文全称，中文解释放在括号外，官方名称和缩写大小写保留

只解释当前报告真正使用且用户可能陌生的内容，先说明是什么，再按理解需要解释用途、机制、条件或与相近概念的区别，写成一条连贯定义，不压成几个标签；直观比喻辅助理解，不代替机制与边界

正式全称来自实际文件或可靠来源，不能猜缩写展开。IT 与 TR 的本版本来源分别是 README 的 Iteration 与 Turn Record；Core 赋予 IT 稳定目标单元含义，TR 承载一次请求、清单、测试和证据。CL-ID/TEST-ID 是记录标识，不为凑术语结构虚构其英文全称

## 关键要点覆盖具体结论，不固定条数

每条使用 `- **具体主旨**：完整自然语句`，让只读本区块的用户仍能知道完整讲解的主要结果、原因、重要限制、未完成项以及下一步归属

写完完整讲解后按实际宏观结论检查覆盖，缺哪项就补哪项，有重复就合并，不固定四条，不用“结果更好”“边界明确”等抽象标题替代实际变化

发布、当前真实入口、构建对应关系、数据保护、费用、外部未完成事项与框架状态都是可能改变用户判断的结论，当前有这些事实时须明确保留；不能用测试数量或比喻取代

## 收口与后续轮次

新轮次、上下文恢复、规则入口改变与最终回复前重新加载当前入口，不依赖聊天记忆；最终回复、TURN 与派生 CURRENT 使用同一正文

检查器只能保证其实际实现的结构，因果是否成立、术语是否有帮助、总结是否覆盖全部宏观结论仍由执行 Agent 逐项复读。若读过规则仍错误执行，责任在执行者；不得用“模型默认简洁”解释后直接免除责任，也不能宣称接入某个平台就自动保证正确语义

## 已安装 VPS 发布副本的兼容更新

新发布副本先读取旧线上实际 AGENTS 和框架历史，不能用本地未安装工作树的短入口覆盖 VPS 的完整 APCF 入口。保留既有 Core 路由段、规则文件、PROJECT_CONTRACT 原始保留稿和已有 IT/REG/运行证据；当前工程回报仅由本文件及 EXECUTOR_REPORTING_RULES.md 引用，不再让历史 BP 模板与新合同并列为当前权威

旧安装器追加的“项目既有约定与本次接入范围”包含当时仅做 Pilot、不改 UI、不部署及 Profile UNRESOLVED 的当轮限制，不是永久禁止用户后续授权的产品工作。迁移时保留这些文字为有明确时间与原轮次的历史附录，新当前范围说明必须引用最新用户授权，不能既删除历史也不能继续把旧范围当当前有效要求

完成入口合并后核对：只有一份 APCF 根入口和规则路由，引用文件真实存在，Core Canonical 字节不变，私有历史仍在 Git 外；发布副本无 Git 时正式 TR 仍可能无法创建，不能通过复制界面代码就宣称修复了既有 Pilot 生命周期阻断
