# 执行 Agent：用户回报格式

## 适用范围

本规则只约束执行 Agent 给用户看的阶段报告、验收回报和最终交付；项目参谋的分析答复不受此格式限制。

本规则属于开发协作约定，不是文章写作规范。不得注入 SourceLoom 给内容模型的提示词、任务包写作要求、论文正文、外部 Skill 或格式检查器。

在本项目的执行 Agent 入口中引用本文件；不要声称已经修改其他项目或保证所有未来 Agent 自动记住。

## 用户侧回报

### BP

- 一句话一个 BP：做什么 → 为什么 → 最终得到什么；附一个贴切、简短的比喻“像……”或“相当于……”。
- 每条尽量 1–2 行，通俗、直接，不用学术腔；数量按核心范围决定，不遗漏授权范围、重要未完成项、费用与数据风险。
- 不在每条里堆内部状态名、十几个文件路径或测试数字。给出用户能理解的结果，再把技术证据放进独立文件。
- 不为了凑比喻改变事实；不能把“正在做／未执行／尚待确认”写成已完成。
- 有权限、不可逆操作、密钥、费用或数据安全问题时，先明确动作与风险；格式不能代替必要的授权确认。

### 验收

**Step 1：功能验收**  
实际操作一次，写明哪个入口、哪条核心功能跑通；未执行就直说。

**Step 2：结果验收**  
检查实际产物是否符合预期，如图表可见、正文未变、资源归属正确、保存重开一致；不以“程序没报错”替代。

**Step 3：异常验收**  
说明实际测试过的错误、缺失、重复、极端情况及结果；合成故障与真实外部故障分开。

**Step 4：连续验收**  
写明连续真实任务／路径的数量、类型、失败与修复后重测范围；不要用一千项单元测试代替，也不要把回执重放算成真实新模型生成。

**Step 5：完成判定**  
明确写：通过／部分通过／未通过；若有剩余问题，写出影响和最小下一动作。部署、Git 推送、内容语义、外部通道各自状态不能互相冒充。

简报末尾给正式入口和一份详细报告链接；用户侧不展开所有日志。

## 固定模板（所有尖括号均须替换为实际事实）

### BP

- <完成的动作>，为了解决<用户问题>，现在<实际结果>；像<简短比喻>。
- <另一核心动作及原因、结果与比喻>。
- <重要限制／剩余项及影响；类比不能淡化问题>。

### 验收

**Step 1：功能验收**  
<实际入口与操作；通过或具体失败。>

**Step 2：结果验收**  
<实际输出与独立核对结果。>

**Step 3：异常验收**  
<实际异常类型与保护结果。>

**Step 4：连续验收**  
<本构建连续运行数量、材料类型、失败与重测；不夸大覆盖。>

**Step 5：完成判定**  
**<通过／部分通过／未通过>**；<剩余项及是否上线、推送、产生费用或改变用户数据。>

正式入口：<已核验地址>  
详细报告：<可实际打开的独立文件链接>

## Agent 侧详细文件

保留真实构建、配置口径、操作记录、输入／输出摘要、原始模型回执、影响范围、数据迁移、备份恢复、费用、异常与残留项。敏感信息按既有安全范围存储，不为了给报告链接而公开私人日志。

不要用这份简报压缩规则约束技术文件的证据完整度，也不要建立新的报告生成模型／发布门禁。
